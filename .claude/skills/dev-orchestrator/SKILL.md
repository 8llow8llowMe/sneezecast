# Development Orchestrator

메인 실행자가 작업을 분류하고 필요한 역할만 선택한다. 역할 정의의 정본은 `.claude/agents/*.md` 이다.
agent 기능이 없는 호스트에서는 메인 실행자가 같은 역할을 순서대로 수행한다.

## 역할과 모델 (2026-09 기준)

역할 파일의 `model` 은 **별칭**으로 적는다. 별칭은 Claude Code 가 그 계열의 최신 모델로 풀어 주므로, 모델이 갱신돼도 파일을 고칠 필요가 없다. 특정 버전에 고정해야 할 때만 전체 ID(`claude-opus-5-5` 등)를 쓴다.

| 별칭 | 현재 해석 | 모델 ID |
|------|-----------|---------|
| `fable` | Fable 5.1 | `claude-fable-5-1` |
| `opus` | Opus 5.5 | `claude-opus-5-5` |
| `sonnet` | Sonnet 5.5 | `claude-sonnet-5-5` |
| `haiku` | Haiku 4.5 | `claude-haiku-4-5-20251001` |

추론 깊이는 frontmatter `effort`(`low` / `medium` / `high` / `xhigh` / `max`)로 역할마다 고정한다. 같은 모델이라도 조사·검토처럼 깊이가 필요한 역할은 effort 를 올리고, 반복 작업은 내려서 비용을 맞춘다.

| 역할 | 모델 | effort | 권한 | 사용 시점 |
|------|------|--------|------|-----------|
| `explorer` | Sonnet | `low` | 읽기 전용 | 파일 탐색, 호출 흐름, 의존성·영향 범위 파악 |
| `crud-implementer` | Sonnet | `medium` | 쓰기 | DTO·매핑·단순 검증·설정·작은 테스트 |
| `implementer` | Opus | `high` | 쓰기 | 일반 기능과 **원인이 확정된** 버그 구현 |
| `bug-investigator` | Opus | `xhigh` | 읽기 전용 | 어려운 버그·트랜잭션·동시성·데이터 정합성 원인 분석 |
| `reviewer` | Opus | `high` | 읽기 전용 | 최종 diff 의 정확성·회귀·보안·테스트 검토 |
| `refactorer` | Opus | `high` | 쓰기 | 동작 보존 리팩토링 구현 |
| `architect` | Fable | `xhigh` | 읽기 전용 | 교차 모듈·서비스 경계·보안·트랜잭션 설계 |

- 읽기 전용은 frontmatter `tools: Read, Grep, Glob, Bash` 로 강제한다 (Write/Edit 미부여). 쓰기 역할은 `tools` 를 생략해 전체 도구를 상속한다.
- Haiku 4.5 는 현재 기본 역할에 쓰지 않는다. Sonnet 5.5 `low` 가 탐색 정확도 대비 비용이 낫다. 대량 반복 조회 전용 역할을 새로 만들 때만 검토한다.

### 세션 모델과 하위 에이전트 모델

- 메인 세션 모델과 하위 에이전트 모델은 **따로 정한다.** 모든 역할 파일에 `model` 이 있는 이유다. 메인 세션의 모델을 하위 에이전트에 상속시키지 않는다 (`model: inherit` 를 쓰는 역할은 없다).
- **메인 세션이 Fable 이면** 작업 계획·설계·범위와 순서 결정·최종 완료 판단은 메인 실행자가 직접 한다. 이 판단을 하위 에이전트에 위임하지 않는다. `architect` 는 메인 세션이 Fable 이 아닐 때 설계 깊이를 보강하는 용도다.
- `Agent` 호출에서 `model` 을 덮어쓰는 것은 예외 처리다(예: 계정에 그 모델이 없을 때). 덮어썼으면 보고에 적는다.
- `fable` 을 쓸 수 없는 계정에서는 `architect` 호출이 거절되거나 다른 모델로 떨어질 수 있다. 아키텍처 작업 전에 `architect.md` 의 `model` 을 `opus` 로 조정하거나 제한을 보고한다.

## 기본 원칙

- 먼저 루트 `CLAUDE.md`(있으면)와 대상 워크스페이스의 엔트리 문서를 읽는다.
- 에이전트 수보다 작업 경계와 증거를 우선한다. 명확한 작업에 조사 역할을 형식적으로 추가하지 않는다.
- 병렬 실행은 서로 독립적인 **읽기 전용** 조사·검토에만 사용한다. 병렬 실행은 **한 메시지 안에 여러 Agent 호출을 넣는 것**이다.
- 동시 실행은 읽기 전용 역할 **2~3개**를 상한으로 본다. 보통 1~2개면 충분하다.
- 공유 파일, 공개 계약, DB 스키마, 도메인 객체를 수정하는 쓰기 역할은 한 번에 하나만 실행한다.
- 하위 에이전트가 다시 에이전트를 낳게 하지 않는다. 역할 선택과 결과 통합은 메인 실행자의 책임이다.
- 커밋·푸시·이슈·PR 생성 같은 저장소 통합 작업은 메인 실행자만 한다 (`/issue`, `/pr`, `/mr` 스킬).
- 사용자가 명시적으로 병렬화·특정 역할·특정 모델을 요청하면 안전한 범위에서 우선한다.

## 작업 분류와 흐름

### SIMPLE

대상: 명확한 CRUD, DTO, 매핑, 단순 검증·설정, 작은 테스트.

1. 위치가 명확하면 탐색 역할을 생략한다.
2. 애플리케이션 코드 변경은 `crud-implementer` 에 맡긴다.
3. 문구나 한 줄 메타데이터처럼 위임 비용이 더 큰 변경은 메인 실행자가 직접 처리할 수 있다.
4. 대상 범위 검증만 실행한다. 설계 역할과 병렬 팀을 호출하지 않는다.

### FEATURE

대상: 일반적인 단일 모듈·화면 기능.

1. 코드 위치나 호출 흐름이 불명확할 때만 `explorer` 를 먼저 실행한다.
2. `implementer` 가 순차적으로 구현하고 테스트한다.
3. 공개 API, 보안, 트랜잭션, 복수 계층에 영향이 있거나 변경량이 큰 경우 `reviewer` 가 최종 diff 를 검토한다.
4. HIGH 이상 지적은 구현 역할이 수정한 뒤 다시 검증한다.

### BUG

대상: 원인이 불명확하거나 재현·상태·트랜잭션·동시성 분석이 필요한 버그.

1. 독립적인 증거 수집이 유효할 때 `bug-investigator` 와 `explorer` 를 병렬 실행한다.
2. 메인 실행자가 두 결과를 실제 코드와 대조해 근본 원인을 확정한다.
3. 원인이 확정된 뒤에만 `implementer` 가 최소 수정한다.
4. `reviewer` 검토와 회귀 테스트를 실행한다.

명확하고 국소적인 버그는 두 조사 역할을 모두 호출하지 않는다.

### REFACTOR

대상: 동작을 보존하면서 구조를 바꾸는 변경.

1. `explorer` 와 `reviewer` 가 현재 의존성·냄새·회귀 위험을 독립적으로 읽기 전용 분석할 수 있다.
2. 중요한 계층이나 모듈 경계를 넘으면 구현 전에 `architect` 를 추가한다.
3. 메인 실행자가 범위와 보존할 동작을 고정한다.
4. `refactorer` 한 명이 순차적으로 수정하고 테스트한다.
5. `reviewer` 가 최종 diff 를 다시 검토한다.

### ARCHITECTURE

대상: 서비스 경계·보안·트랜잭션·메시징·동시성·대형 교차 모듈 설계.

1. `architect` 와 `explorer` 를 병렬 실행한다.
2. 메인 실행자가 설계 제안을 실제 저장소 증거와 대조하고 설계를 확정한다.
3. 구현 요청이 포함된 경우 확정된 계획을 `implementer` 또는 `refactorer` 한 명에게 전달한다.
4. 마지막에 `reviewer` 검토와 관련 검증을 실행한다.

### LARGE_FEATURE

읽기 전용 발견 작업만 최대 2~3개로 병렬화한다. 발견 결과를 하나의 계획으로 통합한 뒤 쓰기는 순차 수행한다. 하나의 이슈·PR 이 30파일을 넘을 것 같으면 먼저 이슈를 쪼개는 안을 사용자에게 제시한다.

## 결과를 다루는 방법

- **검토 보고를 그대로 믿지 않는다.** 근거(파일·행·증거)가 없는 지적은 메인 실행자가 확인한 뒤 반영한다.
- 역할 간 지적이 충돌하면 저장소 `docs/*.md` 를 정본으로 판정한다.

## 완료 조건

다음을 모두 충족해야 완료로 보고한다.

1. 요청한 동작이 구현되었다.
2. 영향 범위가 컴파일되고 관련 테스트가 통과했다.
3. 필요한 수준의 최종 검토가 끝났다.
4. CRITICAL/HIGH 지적이 해결되었다.
5. 불필요한 변경과 겹치는 동시 편집이 없다.
6. 실제 실행한 검증과 남은 위험을 메인 실행자가 보고한다.

**하위 에이전트의 "통과했다" 를 그대로 옮기지 않는다.** 메인 실행자가 검증 명령을 한 번 더 돌린 결과로 보고한다.

## 역할을 추가·변경할 때

- 새 역할 파일에도 `model` 과 `effort` 를 반드시 적는다. 빠뜨리면 세션 모델·세션 effort 를 상속해 비용이 튄다.
- 읽기 전용 역할은 `tools` 를 명시한다. `tools` 를 생략하면 조용히 쓰기 권한을 갖는다.
- 이 문서의 역할 표와 루트 `CLAUDE.md` 의 "작업별 역할 · 모델 배정" 표를 함께 갱신한다.
- 사용자 전역(`~/.claude/agents/`)에 같은 이름의 에이전트가 있어도 **이 저장소의 프로젝트 스코프 정의가 우선한다.**
